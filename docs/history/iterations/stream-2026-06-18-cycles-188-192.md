## Recurring patterns

### 1. `// indirect` go.mod contamination (cycles 188 AND 189)

`go mod tidy` or `go get` sometimes marks newly-added direct dependencies as `// indirect`. This is a systematic failure—two consecutive cycles hit it. DJ catches it reliably, but it requires a fix subagent round-trip each time (~15 min overhead per occurrence).

**Root cause:** Go tooling defaults to marking deps as indirect if they're not explicitly used in the current package's public API surface (even if they are directly imported). TDD subagents add the dependency but don't know to check/clean the annotation.

### 2. Test bypasses the component under test (cycle 188)

The VCR-CASSETTES redaction test called `Redact()` directly rather than through `NewVCRDoer()`. This proved the filter existed but not that the factory wired it. The factory was the public API, and the safety guarantee only holds if the factory applies the filter automatically.

**Root cause:** This is a systematic TDD blind spot. Tests verify implementation exists, not that it's properly wired into the integration seam. Security-critical factories (like cassette filtering) especially need contract tests that exercise the feature end-to-end.

### 3. Testscript `stdout2env` fragility (cycle 190)

Multi-word CLI output ("Created pull request #42: Title") requires regexp extraction, not a full-line capture. The fix (extract `#(\d+)` digits) was clear once the failure mode was understood, but the initial TDD subagent produced a simpler capture assuming clean single-value output.

**Root cause:** TDD subagents don't always anticipate CLI output with spaces and surrounding text. Testscript `stdout2env` should be documented as requiring the filtering user to supply the extraction pattern.
