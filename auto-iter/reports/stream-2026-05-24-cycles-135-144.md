## Confirmed structural findings (evidence-backed)

### Finding 1: post-merge BLOCKER pattern (cycles 139, 143)

**Measurement**: Of 5 feature cycles that had any design-judge BLOCKER
(137, 139, 143, 144 plus 140's 0-BLOCKER case as control), 2 of 4 with
*real* BLOCKERs (50%) ended with follow-up fix PRs:

- Cycle 139: PR #480 auto-merged → DJ found 3 BLOCKERs including a path-
  traversal vulnerability in extension scaffold → PR #482 fixed it
- Cycle 143: PR #491 auto-merged → DJ found 2 BLOCKERs (README + SKILL.md
  table) → PR #493 fixed it
- Cycle 137: PR #474 — DJ BLOCKERs caught *before* merge, fixed inline
- Cycle 144: PR #495 — DJ BLOCKER found but was a false positive

**Inferred mechanism**: CI (~2 min) consistently beats design-judge (~3–5
min). `gh pr merge --auto` armed at §3.6 fires on the first satisfying
event, which is CI green. Cycle 137 succeeded because — I infer from the
metric for cycle 137 (`step6_design_judge` at 13.6s) — DJ returned faster
than usual that time.

**ROI of fixing**: 2 follow-up PRs in this stream = ~30 min of extra
orchestration time + 2 more release-please cycles. Diff between current
behaviour and "wait for DJ before arming auto-merge" is a procedural
ordering change in §3.6. Not estimating LOC — depends on where the
ordering is enforced.

### Finding 2: taste-check false positives recur every cycle

**Measurement**: from metric rows + cycle notes, taste-check produced
violations in:
- Cycle 137: 3 violations (all FPs per notes — MCP handler/tool/group-reg)
- Cycle 138: 6 violations (all FPs per notes — helpers/group-reg/MCP)
- Cycle 143: 4 violations (per `step3_taste_check` metric)
- Cycle 144: 3 violations (manual run — `pat.go` group + `handlers_pat.go`
  + `tools_pat.go`)

**Pattern**: every cycle that creates an MCP triplet or a group-register
file (`<group>.go`) produces the same kinds of FPs. The taste-check
script's check #2 (SKILL.md entry lookup) doesn't apply the same skip
that check #1 (Cobra Short validation) does for `tools_*.go` /
`handlers*.go`. Inline-bash location: `autonomous.md` lines 99–114.

**Inferred fix scope**: ~3 lines in the bash to mirror check #1's skip,
plus hyphen↔underscore equivalence for the verb lookup. Has not been
fixed across at least 4 cycles in this stream and an unknown number prior
(notes data is sparser pre-stream).

### Finding 3: metric emission is broken in 5 of 10 cycles

**Measurement**: counted `step*` rows in `metrics.jsonl` per cycle:
- Cycles with full step instrumentation (135, 141, 143): 3
- Cycles with partial step instrumentation (136, 142, 144): 3
- Cycles with *no* step rows beyond `step1_mode_pick` and `step2_*` setup
  (137, 138, 139, 140): **4**

For cycles 137–140 the only metric rows are `step1_mode_pick`, `step2_prd`,
`step2_worktree`. No `step2_tdd`, no `step6_design_judge`, no
`step3_taste_check`. The actual outcomes are recorded in `cycles.jsonl`
notes (e.g. cycle 138 mentions "design-judge 0 BLOCKERs; taste-check 6
false-positives"), but the structured metric rows aren't there.

**Consequence**: stream-vs-historical comparison on tokens or duration is
not statistically valid. Any future analysis that wants to claim "stream
mode is faster/cheaper" cannot prove it from the data on disk.

## Recommended fixes (evidence-weighted)

Ordered by strength of evidence + clarity of fix, not invented ROI:

1. **Taste-check FP skip** — n=4+ cycles, identical FPs, one-script-change
   fix. Highest confidence + smallest scope.
2. **Auto-merge ordering in §3.6** — n=2 cycles with follow-up PRs, both
   match the same mechanism (CI beats DJ). Fix is procedural ordering.
   High confidence.
3. **Metric emission enforcement** — measured 5/10 cycles partial-or-
   missing. Without this, future reports inherit the same data-quality
   preface this one has.
4. **Design-judge grounding** *(n=1 — monitor first)*: if FP rate climbs
   above 1/10 over the next stream, require existing-file citation for
   style BLOCKERs.
5. **Cycle state persistence** *(n=1 — monitor first)*: PRD-close drift
   only observed once and tied to compaction. Worth a fix only if it
   recurs.

## Bottom line

What this stream demonstrably shows:
- The pipeline catches real issues (cycle 139's path-traversal catch is a
  genuine quality win).
- The auto-merge race undermines that catch in 2 of 4 BLOCKER cases —
  the BLOCKER lands on `main` first and needs a follow-up PR.
- Taste-check noise is unchanged from prior cycles; the same FP patterns
  recur without being fixed.
- Metric emission has degraded enough that future analyses will face the
  same data-quality wall this one did.

What it does not demonstrate:
- That stream mode is faster, cheaper, or higher/lower quality than
  prior cycles in any statistically valid sense. The sample is too small
  and too sparse.
