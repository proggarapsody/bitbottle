# План качества и проверки Bitbottle

**Дата:** 2026-10-18
**Статус:** план; изменения кода, CI и аккаунтам не вносились.

## Цель и критерий заявления

Цель — сделать проверку воспроизводимой для явно перечисленной матрицы провайдеров, версий и платформ. «Полностью рабочая версия» в этом плане означает, что объявленные сценарии на заявленной матрице проходят и релизные артефакты проверены. Это не обещание отсутствия дефектов и не утверждение о проверке каждой возможности Bitbucket.

Проверки делятся на быстрые безопасные PR-проверки, доверенные live-прогоны и проверки артефактов перед публикацией. Локальные команды, неподдерживаемые возможности и ограничения тарифного плана не следует выдавать за пропущенную ошибку провайдера. Поддерживаемая, но недоступная из-за прав или тарифа функция получает статус «не проверена / заблокирована планом», а не «не поддерживается».

## Общий контракт тестирования

Для каждой запускаемой встроенной CLI-команды и каждого MCP-инструмента постепенно уточняется один проверяемый публичный сценарий на поддерживаемом backend. Не нужно добиваться процента строк или писать тест на каждый флаг: нужны понятные требования, устойчивый результат и проверка ошибки там, где это важно.

Каждый тестовый срез должен отвечать на четыре вопроса:

1. **Вывод:** корректный текстовый результат и, где заявлены, JSON-поля, `--jq` и поведение пустого результата.
2. **Эффект:** какой REST/git-запрос отправлен в hermetic-тесте; для live-сценария — какой независимый REST/git-клиент подтвердил ожидаемое состояние.
3. **Ошибка:** ошибка возвращается с ненулевым кодом CLI и ожидаемым stderr либо с `isError` в MCP и правильным кодом/подсказкой, если они предусмотрены.
4. **Ввод:** важные параметры и флаги меняют наблюдаемое поведение: `--json`, `--jq`, `--hostname`, `--limit`, `--web`, `--confirm` и предметные флаги операции. Сам факт передачи флага не считается проверкой его смысла.

Ожидания берутся из пользовательского контракта, API-схемы и заранее подготовленных фикстур, а не копируются из текущей реализации. Подтверждённый дефект сначала воспроизводится красным тестом, затем исправляется и проверяется зелёным. Используются текущие factory, `httptest`, testscript и существующая MCP-зависимость; новый тестовый фреймворк не вводится.

Для пагинации отдельно оставить проверку общего механизма и добавить сценарии операций, где результат больше одной страницы. В частности, `--limit` должен ограничивать суммарное число элементов, а не каждую страницу независимо. Существующие проверки двухстраничной загрузки уже есть в [api_test.go](../../pkg/cmd/api/api_test.go#L306).

## Проверки каждого PR

Эти проверки не требуют секретов и должны оставаться безопасными для fork PR:

- Запускать существующие `make coverage`, `make lint` и build-кросс-компиляцию для всех уже публикуемых целей. `make coverage` включает весь Go/testscript набор, поэтому не добавлять второй запуск `make test-script` без причины.
- Добавлять регрессионный сценарий рядом с публичной командой или MCP-инструментом; изменённый маршрут должен проверяться через реальный публичный интерфейс, а не только приватную функцию.
- Для MCP добавить клиентские тесты через существующий `mcp-go` SDK: запустить сервер через его тестовый сервер, выполнить initialize, проверить список/схемы инструментов, вызвать инструмент и проверить ответ или ошибочную оболочку. Отдельный stdio smoke должен использовать pipe для stdin/stdout, читать протокольный вывод только из stdout и подтверждать вызов хотя бы одного инструмента и ошибку.
- Зафиксировать контракт реестра MCP: реальные зарегистрированные имена, схемы, обязательные параметры и объявленные backend-возможности. Для одиннадцати инструментов без прямой ссылки сначала сопоставить регистрацию, обработчик и существующие общие тесты; затем добавить один успешный и один ошибочный публичный вызов там, где тест действительно отсутствует.
- Тестировать сетевые ошибки, некорректные ответы, retry и классификацию ошибок на поддельном HTTP-сервере. Не проверять реальные rate limits на живом аккаунте.
- Проверять `--confirm`: отказ/отсутствие подтверждения не выполняет опасную запись. Проверять `--limit` на нескольких страницах, `--json` на структуре результата, а `--jq` на выборе поля. Объём кейсов выбирать по важности интерфейса и риска.
- Оставлять секреты и live-провайдеров вне PR из fork. Не использовать `pull_request_target` для запуска кода PR. Секреты доступны только доверенному коду на защищённой ветке; это соответствует рекомендациям GitHub по [безопасному использованию pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

## Nightly: реальные Cloud и Data Center

Расширять текущий [nightly-e2e.yml](../../.github/workflows/nightly-e2e.yml#L13), сохраняя один источник расписания. Сначала запускать его вручную на доверенном коде; после нескольких чистых повторов — включить ночное расписание. GitHub предупреждает, что scheduled-запуски могут задерживаться, а workflow для `schedule` берётся из default branch: [события workflow](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).

Каждый live-job перед тестами обязан проверить выбранный backend, credentials, лицензию для DC, тестовый workspace/репозиторий и ненулевое число ожидаемых сценариев. Если любой обязательный вход отсутствует, job завершается видимым инфраструктурным статусом; нельзя превращать `t.Skip`, пустую выборку или неприменённый шаг в успешное live-прохождение. Разделять статусы: pass, product failure, infrastructure/bootstrap failure, cleanup failure, capability not applicable, blocked by plan.

Выполнять подготовку фикстур независимым REST/git-клиентом, затем собирать тестируемый CLI из SHA текущего workflow и запускать его публичные команды. Для MCP поднимать отдельный `bitbottle mcp serve` дочерний процесс, выполнять протокольный handshake, `tools/list` и выбранные `tools/call`; результативные изменения подтверждать независимым REST/git-клиентом.

Начать с вертикального сценария: создать временный репозиторий и ветку, загрузить небольшой Git-исторический набор, создать PR от автора, отредактировать его и проверить результат независимым запросом. Следующие сценарии добавлять постепенно:

- PR и commit files: добавленный, изменённый, удалённый и переименованный файл; пробелы и Unicode в пути; небольшой бинарный файл; пустой diff; проверить каждую запись.
- Достаточно веток/PR для перехода через границу пагинации; сравнить обычный и JSON/jq-результат и ограничение общего числа через `--limit`.
- Раздельные автор и reviewer: создание/редактирование PR, комментарий или задача, approval; отдельный PR для decline, и merge только в отдельном проверяемом сценарии.
- Ветка/тег: создать, прочитать, удалить с подтверждением; конфликт с защитой ветки.
- Неверный token, read-only пользователь, отсутствующий репозиторий/PR: проверить ожидаемый отказ без нежелательной записи.

В герметичных проверках покрывать общий контракт всех операций постепенно; live smoke на каждом ночном прогоне сначала сосредоточить на критических семействах. После измерения можно распределить более широкий набор сценариев по ночам и вести матрицу покрытия, чтобы не запускать тяжёлый полный каталог на каждый PR. Специфичный для провайдера сценарий выполняется только при наличии объявленной поддержки. Ограниченная тарифом возможность не считается неподдерживаемой. Pipelines не запускать по умолчанию: отдельный opt-in нужен только для теста, который действительно проверяет этот продуктовый маршрут.

Сохранять tested commit SHA, точную версию backend, набор scenario IDs и счётчики run/pass/fail/skip, длительность, sanitized-логи и cleanup manifest. Записывать token scopes без значений. Диагностику собирать до teardown; удаление запускать всегда, а при старте проверять manifest и подчищать только старые ресурсы с уникальным префиксом данного проекта.

## Бесплатная инфраструктура и ограничения Data Center

Для CI можно использовать стандартный GitHub-hosted Linux runner без постоянно включённого VPS. Для публичного репозитория GitHub документирует 4 CPU, 16 GB RAM и 14 GB SSD для standard Linux runner; характеристики и квоты зависят от видимости репозитория и тарифа: [спецификация runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners). Это делает локальный DC stack разумным экспериментом, но не доказывает, что он уложится в бюджет: измерить холодный старт, память, диск и длительность до обязательного nightly-gate.

Data Center требует Bitbucket, PostgreSQL и внешний поиск. Предлагаемый disposable Compose — Bitbucket 10.2.x с точным доступным patch и digest, PostgreSQL 16 и совместимый OpenSearch 2.x; версии нужно подтвердить при реализации по [supported platforms 10.2](https://confluence.atlassian.com/bitbucketserver102/supported-platforms-1791788731.html) и [официальным образам Bitbucket](https://hub.docker.com/r/atlassian/bitbucket). Сервис поиска обязателен для выбранного образа; отключение индексации не следует принимать за отсутствие зависимости: [настройка поиска](https://confluence.atlassian.com/bitbucketserver102/configure-bitbucket-s-code-search-index-1791788635.html). Compose, внутреннюю сеть и удаляемые volumes запускать только по запросу nightly; старый `atlassian/bitbucket-server` больше не является используемым образом.

**Ключевое ограничение лицензии:** на 18 октября 2026 нельзя планировать DC-тесты как гарантированно бесплатную постоянную lane. Действующая инструкция trial сообщает, что с 30 марта 2026 self-generated trial keys недоступны, и указывает путь через контакт с Atlassian для существующих клиентов Data Center; после окончания 30-дневного trial инстанс становится read-only: [инструкция trial](https://confluence.atlassian.com/bitbucketserver/get-a-bitbucket-data-center-trial-license-1188400764.html). При этом общая страница загрузки всё ещё описывает полностью функциональный 30-дневный trial: [загрузка Bitbucket DC](https://www.atlassian.com/software/bitbucket/download/data-center). Это противоречивые официальные страницы; право получить ключ для этого проекта не подтверждено. Dev/test лицензия также ограничена подходящими существующими коммерческими или академическими лицензиями: [лицензирование Data Center](https://www.atlassian.com/licensing/data-center).

Следовательно, DC lane остаётся заблокированной до получения законного ключа или доступа к уже авторизованной тестовой установке. Это не блокирует hermetic PR-проверки и Cloud Free пилот, но Cloud pass не подтверждает DC-покрытие. Не делать вывод, что Atlassian обязательно выдаст trial, и не закладывать продление временного ключа как постоянное CI-решение.

Cloud Free — доступная первая live-lane: план поддерживает до пяти пользователей и неограниченное число репозиториев, при соблюдении опубликованных условий тарифа: [планы Cloud](https://support.atlassian.com/bitbucket-cloud/docs/manage-your-plan-and-billing/). Использовать отдельный workspace, scoped API token и только синтетические данные. Тестовые actor-аккаунты — обычные авторизованные участники workspace; отдельные reviewer/read-only роли добавляются только если они нужны сценарию. API tokens поддерживают Bearer auth: [API tokens](https://support.atlassian.com/bitbucket-cloud/docs/using-api-tokens/). Не отправлять приглашения внешним пользователям и не выполнять действия в несвязанном workspace.

Для Cloud bootstrap и тестируемые identity разделяются. Bootstrap создаёт уникальный временный repository и пользователей/права, если это разрешено. Сам тест использует обычный авторский или reviewer token с минимальными нужными правами. Членство workspace настраивается один раз; repositories создаются на запуск. Уникальное имя включает run ID, attempt и случайный суффикс; manifest хранит точный owner/workspace/repo allowlist. Cleanup удаляет только ресурсы, перечисленные в manifest, и проверяет результат удаления. Для Cloud PR сначала выполнить decline, затем удалить временный repository; cleanup failure — отдельный красный результат.

## Проверки перед публикацией

Release candidate проверяется по тому же commit SHA и digest, что попадут пользователю. Ни green nightly на другом SHA, ни одна кросс-компиляция не заменяют проверку артефакта-кандидата. Release-PR не должен пропускать обязательные test/lint/build шаги: сейчас release-please workflow имеет условия пропуска для этих шагов, а release workflow отдельно собирает и публикует. См. [условия CI](../../.github/workflows/ci.yml#L24) и [release workflow](../../.github/workflows/release.yml#L52).

Для кандидата нужно:

- Запустить обязательные PR-проверки на SHA релизного кандидата и nightly-сценарии на той же сборке для всех backend, которые будут перечислены как подтверждённые.
- Скачать созданные GoReleaser архивы и проверить запуск CLI на доступных native runner OS/архитектурах; кросс-компиляция остаётся только сборочной проверкой. Текущие заявленные цели: Linux amd64/arm64, macOS amd64/arm64, Windows amd64: [конфигурация GoReleaser](../../.goreleaser.yaml#L10).
- Проверить `--help`, `--version`, один безопасный read-only CLI вызов и MCP stdio протокол из установленного релизного бинаря/контейнера, а не только `go test`.
- Проверить `npm pack` и установочный smoke wrapper, а также Docker entrypoint для MCP stdio; проверить содержимое архивов и отсутствие временных credentials/configuration files. Текущий dry-run подтверждает snapshot и упаковку npm, но не install/real-binary smoke: [release dry run](../../.github/workflows/release-dryrun.yml#L41).
- Зафиксировать SHA, artifact digest, Go version, версии зависимых сервисов, сценарии и cleanup status. Текущая конфигурация описывает release build и отдельный snapshot dry run, но не установленный путь передачи тех же байтов от QA к публикации: [release.yml](../../.github/workflows/release.yml#L52) и [release dry run](../../.github/workflows/release-dryrun.yml#L41). Поэтому сначала сделать ограниченный spike: доказать поддерживаемый текущими OSS-инструментами способ проверить именно candidate bytes до публикации либо воспроизводимо связать SHA и итоговый digest. Одинаковый SHA сам по себе не доказывает одинаковые байты; не считать эту проверку завершённой до демонстрации пути.

Платформы, на которых нет доступного native smoke runner, явно помечаются непроверенными или требуют отдельного подтверждения перед широким заявлением о поддержке. Факт сборки для целевой ОС не означает, что бинарь запускался на ней.

## Этапы и критерии завершения

### Этап 0 — стабилизировать исходную точку

- Воспроизвести и локализовать падение `TestScript/commit_files_cloud`; добавить регрессионный тест, исправить дефект отдельно.
- Убедиться, что acceptance для live-среды не может дать зелёный результат при незаданном выбранном backend, пустом наборе сценариев или `t.Skip`.

- Согласовать список runtime операций и исправить неверные соответствия из карты до новых тестов.
- **Готово, когда:** повторный `make coverage` зелёный; нет скрытого skip в обязательном job; каждый оставшийся skip/infra-unavailable виден и классифицирован. Live-секреты в PR не нужны.

### Этап 2 — от пилотных семейств к полной hermetic-матрице CLI/MCP

- **Решение 2026-10-19:** каталог и первый пилот влиты через #686. Для текущего выпуска обязательный локальный рубеж — [зафиксированный критичный профиль](2026-10-19-critical-release-scenarios.md), проверяемый `make qa-critical-check` по полному прогону и сохранённым доказательствам. Полный каталог и его пробелы остаются видимыми; исчерпывающее завершение проверяет `make qa-matrix-check` в последующей работе. [Прежний срез](2026-10-19-cli-mcp-matrix-round2.md) остаётся историческим, а не результатом нового прогона.
- Проверить общую матрицу всех builtin операций и capability declarations; классифицировать локальные команды, поддерживаемые backend, реальные unsupported и пробелы карты.
- Добавить сквозные hermetic-тесты для вывода/JSON, сетевого эффекта, ошибочного ответа, важных flags и пагинации в приоритетных командных семействах.
- **Пилотный рубеж:** критичные публичные семейства имеют независимые ожидания, проверку результата и ошибки; подтверждённые дефекты воспроизводятся регрессиями.
- **Текущий release DoD этапа 2:** каждая строка зафиксированного критичного профиля имеет проверенные публичные success/error-сценарии и осмысленные проверки вывода, эффекта и ввода по применимости. Все важные входы покрыты, кроме четырёх явно отложенных merge-флагов с точной неопределённостью в профиле. Gate повторно проверяет полный прогон, test events, исходники и hashes; пропуск, отсутствие доказательства или устаревший результат дают отказ. Остаток всего каталога публикуется как явный backlog, без заявления о его завершении.
- **Полный hermetic DoD — последующая работа:** у каждой поддерживаемой builtin CLI-команды и MCP-инструмента есть ссылка на публичный успешный и ошибочный сценарий, а также осмысленные проверки вывода, эффекта и ввода по применимости. Важные флаги перечислены и проверены; неприменимость объяснена. Неизвестные и несопоставленные случаи не засчитываются как завершённые. Не требуется тестировать каждую комбинацию флагов.
- Live-проверка остаётся отдельной матрицей по провайдеру, версии и доступным правам; недоступные платные возможности не считаются проверенными.

### Этап 4 — Data Center доступ и пилот

- Сначала подтвердить право на trial key или доступ к авторизованной тестовой установке. Затем вручную измерить Compose cold start, readiness, ресурсы, setup и повторную очистку.
- Если ключа/доступа нет, сохранить честный статус `DC blocked by license/access`, продолжая Cloud и hermetic работу.
- **Готово, когда:** на конкретно названной версии DC прошёл один реальный сценарий CLI и MCP с независимой проверкой и cleanup. Временный trial не считается постоянным решением CI.

### Этап 5 — Nightly и prerelease policy

- Расширять существующий nightly для повторов и сценариев; при доказанной стабильности включить расписание и ограниченную версионную матрицу.
- Привязать prerelease job к SHA и digest кандидата; добавить реальные native smoke, npm install и контейнерный MCP smoke.
- Если DC trial получить нельзя или он истёк, выпуск разрешён только с точной видимой пометкой «DC не проверен live» в QA-отчёте и release notes. Отсутствующий или пропущенный live-прогон DC остаётся unavailable/skipped, никогда pass. Это исключение не отменяет остальные обязательные gates и не оправдывает обнаруженную регрессию продукта в DC.
- **Готово, когда:** выбранные обязательные сценарии имеют явные run/pass/fail/skip статусы, cleanup проверен, а spike доказал проверяемый путь candidate bytes → публикация или SHA-bound воспроизводимый digest. Одинаковая версия исходника без проверки артефакта недостаточна; все остальные обязательные проверки должны пройти.

## Открытые условия

1. Какой законно доступный DC license key или авторизованный тестовый сервер можно использовать? До подтверждения DC live lane остаётся недоступной.
2. Какой минимальный поддерживаемый DC patch/version и набор платформ команда хочет сертифицировать? План не расширяет текущую матрицу автоматически.
3. Какие операции требуют paid Cloud features? До доступного entitlement они помечаются как blocked by plan, а не как unsupported или passed.

Эти условия определяют матрицу финального заявления. Само выполнение плана не создаёт entitlement и не превращает пропущенный backend в проверенный. Разрешённый выпуск с пометкой «DC не проверен live» не является заявлением о полной проверке обоих backend.
