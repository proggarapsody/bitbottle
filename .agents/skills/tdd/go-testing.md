# Go testing

This is working guidance, not a new repository gate; follow explicit project instructions and existing test conventions.

Use Go's standard `testing` package and the project's existing assertion tools. Treat table-driven tests as an organization technique: use them for similar cases of the same behavior, with named subtests; split cases into separate tests when setup or branching obscures what each case proves. See the [Go testing package](https://pkg.go.dev/testing), [subtests guidance](https://go.dev/blog/subtests), and [Uber's table-test guidance](https://github.com/uber-go/guide/blob/master/style.md#test-tables). These are practices to choose from, not company-wide requirements.

Keep expectations independent of the implementation: derive them from a provider specification or documentation, a known example, or a confirmed bug. A local HTTP fake verifies the request and response contract encoded by its fixture; it does not establish the live provider's current behavior. For CLI and MCP paths, assert caller-visible output, exit or returned errors, state changes, and important flags. At an HTTP boundary, method, path, query, headers, and payload are observable contract when they affect provider behavior. Use a fake at the external boundary when it makes those effects deterministic; avoid mocking internal collaborators just to assert call sequences.

Choose the test whose failure would catch the regression: do not mirror every method or layer mechanically. Keep names specific and failure messages useful, following [Go's test comment guidance](https://go.dev/wiki/TestComments). For an audit where assertion strength is uncertain, run the relevant test against the unchanged baseline, introduce one targeted defect or negative control, and confirm the test fails for the intended reason; restore production code and rerun. This is a diagnostic for consequential or uncertain assertions, not a ritual for every small edit. Keep hermetic tests, live-provider checks, and skipped acceptance runs as distinct evidence; a skip is not a live pass.

These recommendations are informed by [Google's testing chapters](https://abseil.io/resources/swe-book/html/ch12.html) and [test infrastructure chapter](https://abseil.io/resources/swe-book/html/ch13.html), plus the [GitHub CLI testing guide](https://github.com/cli/cli/blob/trunk/docs/testing.md) and [Terraform acceptance testing guide](https://developer.hashicorp.com/terraform/plugin/testing/acceptance-tests). Those projects illustrate choices for their contexts; they do not impose their dependencies or acceptance setup on Go projects here.
