# Практики тестирования Go: обзор источников

**Статус:** обзор источников и предложение для обсуждения, не принятая политика Bitbottle. **Объём:** выборочная проверка публичных рекомендаций и текущих категорий тестов; это не полный аудит качества тестов. Здесь нет утверждения, что все ранее обсуждавшиеся 125 пар тестов выполнялись против live-провайдера. DC не проверен live; функция Cloud auto-merge отложена. Изменения релиза не входят в этот обзор.

Практические рекомендации из этого обзора приняты в [локальном Go testing guide](../../.agents/skills/tdd/go-testing.md); их применение и границы доказательств описаны в [аудите критичных тестов](../quality/2026-10-20-critical-test-audit.md). Источники и исходное предложение ниже сохранены.

## Общие ориентиры

У компаний нет единого универсального стандарта тестирования: публичные руководства описывают разные практики и контексты. В Go тесты обычно лежат в файлах `*_test.go`, используют пакет `testing` и функции `TestXxx`. Table-driven tests — техника организации набора случаев, а не отдельный уровень тестирования. [Документация Go](https://go.dev/doc/tutorial/add-a-test) и [пакет testing](https://pkg.go.dev/testing) показывают стандартную модель. В Uber Style Guide таблица подходит для похожих простых случаев; если проверка содержит сложные условия и отдельный harness, её рекомендуют разделить на понятные тесты ([Uber Go Style Guide](https://github.com/uber-go/guide/blob/master/style.md#test-tables)).

`fxtest.New`, `RequireStart` и `RequireStop` помогают тестировать lifecycle приложения, построенного на Uber Fx ([документация fxtest](https://pkg.go.dev/go.uber.org/fx/fxtest), [тесты Fx App](https://github.com/uber-go/fx/blob/master/app_test.go)). Это библиотечный инструмент для Fx lifecycle и само по себе не даёт основания добавлять Fx в CLI.

Полезное общее направление — проверять публичное поведение и результаты, которые видит пользователь, а зависимости по возможности заменять реализациями, близкими к настоящим. Это не означает обязательный внешний сетевой вызов в каждом тесте. В главах о тестировании и инфраструктуре тестов Google описаны проверки поведения и управление зависимостями ([глава 12](https://abseil.io/resources/swe-book/html/ch12.html), [глава 13](https://abseil.io/resources/swe-book/html/ch13.html)). Для Go также важны ясные сообщения об ошибках и прямые проверки ([TestComments](https://go.dev/wiki/TestComments)); subtests дают именованные подслучаи и удобный выбор запуска ([Go blog: subtests](https://go.dev/blog/subtests)); fuzzing можно применять дополнительно для парсеров и других функций, принимающих широкий диапазон входов ([Go fuzzing tutorial](https://go.dev/doc/tutorial/fuzz)). Ни одна из этих техник сама по себе не задаёт уровень или полноту тестирования.

## Практики из близких инструментов

Документация GitHub CLI разделяет обычные изолированные тесты, проверки конструктора и флагов, проверки результата выполнения, а также HTTP- и Git-заглушки с ожидаемыми операциями. Live-проверки отделены от обычного запуска тестов и не используют аккаунт оператора как неявную зависимость ([GitHub CLI: testing](https://github.com/cli/cli/blob/trunk/docs/testing.md)). Acceptance-тесты Terraform проверяют реальный жизненный цикл и отдельно требуют проверить уничтожение созданных ресурсов; запуск явно включается для acceptance-контура ([Terraform acceptance tests](https://developer.hashicorp.com/terraform/plugin/testing/acceptance-tests)). Эти примеры показывают варианты организации, а не стандарт, который Bitbottle обязан копировать.

Статические контрактные инварианты и контракт API провайдера — разные вещи. Локальный HTTP fake подтверждает совместимость с заданным fixture и проверяемыми ожиданиями, но не доказывает, что реальный провайдер сейчас поддерживает этот запрос или ответ. Для этого нужна отдельная live-проверка. Число операций провайдера в тестах не доказывает качество или покрытие всех вариантов поведения. Библиотеки assertions различаются между проектами; этот обзор не даёт причины мигрировать Bitbottle на другой framework.

## Предложение для обсуждения

Для важных сценариев можно кратко фиксировать карточку проверки: поведение пользователя; источник ожидания (спецификация, документация провайдера или подтверждённый дефект); вход и предусловия; видимый результат, ошибка или изменение состояния; запрещённые побочные эффекты; граница теста; регрессия, которую тест должен обнаружить. Одно и то же утверждение не нужно механически дублировать на каждом слое.

Например, при отказе Cloud auto-merge полезно проверить код `pr.automerge.unavailable`, полезную подсказку, отсутствие успешного результата и отсутствие HTTP-запроса. Для обычного merge важно подтвердить состояние `MERGED`, а не считать любой ответ 2xx доказательством успешного слияния. Такой набор — целевое предложение для обсуждения, не действующая политика.
