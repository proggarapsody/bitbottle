## Predictability and algorithm consistency

### New recurring pattern: auto-merge race (cycles 176, 177)

CI completes in ~2 minutes. DJ completes in ~3-5 minutes. When a BLOCKER
is present, DJ discovers it after the PR has already auto-merged. This
produces a second PR in the same cycle that isn't tracked under the
original scope.

This pattern appeared in cycles 135–144 (fixed via DJ ordering), was
absent in 145–154, and recurred in 2 of 2 BLOCKER-containing cycles in
this stream. The ordering fix helps when DJ runs before CI; it does not
help when CI finishes first and auto-merge fires during DJ execution.

### Dispatch violations (cycles 168–169)

Cycle 168: orchestrator applied a DJ fix (isCloud dead branch) inline
rather than dispatching a fix-agent. Cycle 169: orchestrator performed
full TDD inline rather than dispatching a TDD subagent. Both violate the
"orchestrator is shell-only" rule documented in project memory. The
violations were logged to memory and corrected by cycle 172.

**Root cause signal**: both violations occurred in the opening cycles
where the orchestrator had more context than normal (user had specified
which issues to open). High-context opening may lower dispatch discipline.

### Socket drops (cycles 176, 177)

Two agent timeouts in the final two cycles. Cycle 176: TDD subagent
dropped mid-run; finish-agent completed partial work. Cycle 177:
post-stream Opus analysis timed out (did not affect ship outcome). n=2
in the same stream's tail end; may be session-length related or
infrastructure coincidence. Not enough data to call a pattern.

## Recommended fixes (ranked by ROI)

### Fix 1: DJ-then-wait gate before auto-merge arm (HIGH ROI, ~20 LOC)

**Problem**: CI (~2min) fires before DJ (~3-5min) completes; auto-merge
arms on CI green; DJ BLOCKER arrives post-merge. n=2 BLOCKERs escaped
in this stream.

**Fix**: after pushing the PR, wait for DJ to finish and produce VERDICT
before arming auto-merge. Current sequence:
```
push → arm auto-merge → await CI → (DJ still running) → merge
```
Required sequence:
```
push → run DJ → if VERDICT=SHIP → arm auto-merge → await CI → merge
```

DJ must complete before auto-merge is armed. If DJ returns BLOCKER,
dispatch a fix-agent before arming.

**Files**: `.claude/commands/auto-iter.md` (~5 lines around `gh pr merge
--auto`), `docs/workflows/iteration-cycle/README.md` §3.5–3.6 (~10
lines), `docs/workflows/iteration-cycle/quickref.md` anti-patterns
section (~5 lines).

**Effort**: ~20 lines changed across 3 files.

### Fix 2: enforce dispatch for DJ fixes (MEDIUM ROI, ~5 LOC)

**Problem**: cycles 168–169 show that when the orchestrator has high
context at stream open, it bypasses dispatch for both DJ fixes and full
TDD. The rule exists in project memory but not as an enforced check.

**Fix**: add an explicit pre-merge-mechanical check (or quickref
anti-pattern entry) that names "DJ fix applied inline" as a BLOCKER on
commit, requiring the commit note to include a dispatched-agent
reference. Alternatively, a tighter constraint in auto-iter.md: after
any DJ BLOCKER, the next action MUST be `dispatch fix-agent` with no
inline editing.

**Files**: `docs/workflows/iteration-cycle/quickref.md` anti-patterns
(~3 lines), `.claude/commands/auto-iter.md` §DJ-response (~3 lines).

**Effort**: ~6 lines.

### Fix 3: token emission to cycles.jsonl (LOW ROI for correctness, HIGH for observability)

**Problem**: 0/10 cycles in this stream emitted token data. The field is
present but zeroed (`"tokens":0`). Without real token data,
stream-vs-stream cost comparisons are impossible.

**Fix**: identify where log-cycle.sh or the equivalent metric-emission
step pulls token counts and ensure subagent token totals are piped
through. If the orchestrator doesn't have access to subagent token
summaries, add a post-agent summary step that reads the agent's reported
token count and writes it to the cycle log.

**Files**: `auto-iter/scripts/log-cycle.sh` (primary source), possibly
`auto-iter/scripts/metric.sh`.

**Effort**: unknown until the emission path is read; likely ~10 lines.

### Fix 4: socket-drop recovery protocol (LOW ROI, 1-2 sentences in docs)

**Problem**: cycles 176 and 177 each had an agent timeout. The finish-
agent approach (cycle 176) worked but is ad-hoc. No recovery protocol
is documented.

**Fix**: add a `## Socket drop recovery` subsection to
`docs/workflows/iteration-cycle/README.md` describing:
- TDD subagent timeout → dispatch finish-agent with partial commit hash
- Analysis agent timeout → skip post-stream analysis; write partial note to cycles.jsonl

**Files**: `docs/workflows/iteration-cycle/README.md` (~10 lines).

**Effort**: ~10 lines; low urgency (n=2, may be session-length artifact).

## Bottom line

The stream shipped 10/10 features with 0 broken states on `main` at any
point. DJ accuracy was 100% on BLOCKERs (2/2 real). These are positives.

Two recurring failure modes assert themselves:

1. **Auto-merge race** — the most actionable finding. Fix 1 above
   (arm auto-merge only after DJ completes) would have prevented both
   follow-up PRs in this stream. This is a workflow sequencing change,
   not a code change. It should be applied before the next stream.

2. **Dispatch violations at stream open** — corrected mid-stream and did
   not recur in cycles 172–177. The discipline is present; what's missing
   is a mechanical guard that makes inline orchestrator edits impossible
   rather than merely discouraged.

Cycles 172–177 post-correction represent the ceiling: 6 clean cycles
with real BLOCKERs caught by DJ, dispatch-clean, no rework. Getting the
entire stream to that bar requires Fix 1 and Fix 2.
